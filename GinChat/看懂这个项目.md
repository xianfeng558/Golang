# 看懂 GinChat

把这个项目看成一个进程、一条 WebSocket、三样 Redis 数据。按下面这些点看，代码就能对上，不必先把聊天系统的书读完。

启动、接口和排错仍以 [使用文档.md](使用文档.md) 为准。本文只回答：要懂哪些东西，才算看懂这个项目。

## 先记住项目边界

只有一个进程，默认听 `:8080`。页面和表单走 HTTP，聊天走 WebSocket。没有第二个服务，也就没有服务发现。

```text
浏览器
  → Gin（页面、注册、登录、好友、群、上传）
    → service（取出表单字段，决定成功还是失败）
      → models（写 MySQL，或把消息交给某条 WebSocket）
        → MySQL / Redis
```

聊天页另外开一条长连接：

```text
浏览器 WebSocket  /chat?userId=..&token=..
  → models.Chat 核对令牌，把这条连接放进内存表
    → 对方发来消息时，写进这条连接
    → 同时把私聊原文放进 Redis
```

工作目录必须是 `D:\golang\GinChat`。配置、模板、静态文件都相对这个目录。只有一个 `go.mod`，模块名是 `ginchat`。`go run`、`go test`、`go mod tidy` 都在这个目录里做。

`docs/docs.go` 是 swag 生成的，阅读时跳过。`release/` 是以前打包出去的一份资源，`go run` 不读它。

用户、好友、群在 MySQL 库 `ginchat`。在线状态和私聊记录在 Redis。`message` 表留着结构，私聊正文实际在 Redis。

## 看懂代码所需要的东西

按这个顺序就够。每一项都只要懂到「能解释这个项目里的那一处」。

### 1. 一条私聊怎么从浏览器到另一个浏览器

先有两个已经登录的用户。聊天页在 `views/chat/foot.html` 里连接：

```text
ws://127.0.0.1:8080/chat?userId=3&token=登录返回的Identity
```

`token` 必须等于 `user_basic.identity`。对不上，连接升级会被拒绝，HTTP 状态是 401。

用户 3 给用户 4 发「你好」时，页面发出的 JSON 大致是：

```json
{"userId":3,"TargetId":4,"Type":1,"Media":1,"Content":"你好"}
```

服务端接着做这些事：

```text
用户 3 的 WebSocket
  |  Type=3 只刷新心跳，不往下走
  |  Type=1 私聊：找到用户 4 的连接，把这段 JSON 原样写回去
  |  同时 ZADD 到 Redis 键 msg_3_4
用户 4 的页面 onmessage 收到同一段 JSON
```

转发时用的是浏览器发来的那一段字节。如果在服务器里重新编一次 JSON，字段会变成 `UserId`，页面读的是 `data.userId`，昵称和内容就对不上。

`Type`：1 私聊，2 群聊，3 心跳。`Media`：1 文字，2 表情，3 语音，4 图片。群消息的 `TargetId` 是群 ID。服务端查出群里的人，跳过发送者，再写到其他人的连接上。群消息只负责送达，不写进两人的私聊记录。

### 2. 一条连接上有哪些协程，各自保护什么

`gorilla/websocket` 把一次普通 HTTP 请求升级成长连接。升级成功之后，这条连接不再走 Gin 的返回值。

同一条连接上有读协程和写协程。读循环看到 `Type=3` 就当心跳，其它消息交给 `dispatch`。写的时候不直接在读循环里 `WriteMessage`。消息先进入 `DataQueue`，由写协程取出再写。队列最多 50 条，满了就丢掉新的并打日志。

三处保护的不是同一份数据：

| 东西 | 保护什么 |
| --- | --- |
| `sync.RWMutex` | 在线连接表 `clientMap`。查用读锁，登记和删除用写锁 |
| 原子变量 | 这条连接的心跳时间。读协程和定时器都会碰它 |
| `writeMu` | 这条 socket 的写和关。gorilla 的连接不能同时 `Write` 和 `Close` |

连接关掉时用 `sync.Once` 保证只清理一次：从内存表删掉、关掉通知通道、删掉 Redis 里的在线标记、关闭连接。读协程和定时器可能同时发现它该关了。

同一时刻，一个用户在这个进程里只有一条连接。后连上的会替换先连上的。

### 3. Redis 的三把键

| 键 | 值 | 什么时候写 |
| --- | --- | --- |
| `online_用户ID` | 连接的远端地址 | WebSocket 连上时，心跳时续期。默认 4 小时 |
| `msg_较小ID_较大ID` | 有序集合，成员是私聊 JSON | 只在 `Type=1` 时写入 |
| `websocket` | 发布订阅频道 | 只有演示接口 `/user/sendMsg` 使用，聊天页不走它 |

键名把两个 ID 从小到大排。3 看 4 的记录，和 4 看 3 的记录，是同一把钥匙。分数是发送时的毫秒时间。`/user/redisMsg` 的 `start` 和 `end` 是有序集合的下标，不是用户 ID。页面第一次取 0 到 9。

投递前会看收件人是不是在本进程的内存表里，以及 `online_` 键还在不在。

### 4. 登录令牌和密码摘要不是同一件事

密码是 `Md5Encode(明文 + 盐)`。盐是注册时生成的 6 位数字，存在 `salt`。登录时用同样的盐再算一次，和库里的 `pass_word` 比较。MD5 很快，不适合保护真实密码。这里只为了看懂「盐 + 摘要」这条链路。

登录令牌是 `MD5Encode(用户ID-当前纳秒)`，写成大写，存在 `identity`。它不是密码。页面把这个值放进 `/toChat` 的 `token`，WebSocket 再拿来核对。重新登录会换一张令牌，旧的 `token` 连不上。

响应里用 `json:"-"` 去掉了 `PassWord` 和 `Salt`。

注册页的确认密码字段叫 `Identity`，因为页面输入框绑的是这个名字。它只在注册表单里用，和登录后的令牌列不是一回事。

### 5. 好友为什么是两行，申请为什么另有一张表

`contact` 里 `type=1` 是好友，`type=2` 是群成员。`OwnerId` 是这条关系属于谁，`TargetId` 是对方用户或群。

马上加好友的 `/contact/addfriend` 会插两行：A 的名单里有 B，B 的名单里也有 A。这两次插入在同一个事务里。建群也是：先插入 `communities`，再把群主写成一条 `type=2` 的关系。事务对象是 `tx`，插入必须打在 `tx` 上。

`/contact/addfriend` 仍然马上成为好友，聊天页不用改。另外三条接口用来讲「申请和关系分开」：

| 路径 | 作用 |
| --- | --- |
| `POST /contact/apply` | 写入 `friend_apply`，状态 0 |
| `POST /contact/applyList` | 发给这个人的待处理申请，列表在 `Rows` |
| `POST /contact/applyReply` | `accept=1` 时在一个事务里写成双向好友 |

已经是好友、重复的待处理申请、自己加自己，都不会插入。只有被申请人能处理。

`group_basic` 是旧群表。当前建群写的是 `communities`，这张旧表只留在自动迁移里。

### 6. 两套 JSON，页面已经按它们写好了

登录、注册、改资料、用户列表用小写：

```json
{"code":0,"message":"登录成功","data":{"ID":7,"Name":"ada","Identity":"..."}}
```

好友、群、上传、历史消息用大写：

```json
{"Code":0,"Msg":"添加好友成功","Data":0,"Rows":null,"Total":null}
```

列表把数组放在 `Rows`。历史消息的 `Rows` 才是消息数组。

### 7. 心跳、UDP 和上传，知道边界就行

页面每 10 秒发一次心跳。定时器先等 3 秒，之后每 30 秒看一遍连接。默认 60 秒没有心跳就关闭连接，并删掉 Redis 里的 `online_` 键。心跳时间在内存里，不回写 `user_basic.heartbeat_time`。

`models.StartUDP` 监听 `3001`，把业务消息广播到 `255.255.255.255`。另一台机器上的进程如果也在听，就会收到并再投递给自己的在线用户。本机广播会把自己发出去的包又收回来，`dispatch` 用内容的 MD5 记一分钟，第二次看见就丢掉。监听失败只打日志，同一台机器上的两个浏览器仍然能聊。

默认上传写到本机 `asset/upload`。`UploadOSS` 留在代码里，路由没有调用它。

## 建议顺着这些文件读

手写的 `.go` 用中文注释说明这个类型或函数在业务里做什么。

1. `config/app.yml`：端口、数据库和心跳各是哪个字段。
2. `main.go`：进程启动的顺序。配置失败或数据库失败会退出。
3. `router/app.go`：一条 URL 落到哪个函数。`/chat` 是聊天，`/user/sendMsg` 只是 Redis 发布订阅的演示。
4. `service/userservice.go` 的 `CreateUser` 和 `FindUserByNameAndPwd`：表单字段和 `code` / `message`。
5. `models/user_basic.go`：盐、摘要和令牌分别写进哪一列。
6. `utils/md5.go`：摘要怎么算。对照 `utils/md5_test.go`。
7. `index.html` 和 `service/index.go`：登录页怎么拼出来，成功后跳到哪里。
8. `views/chat/foot.html` 里的 `initwebsocket`、`sendtxtmsg`、`heartbeat`：它发出的 JSON 长什么样。不必通读整个文件。
9. `models/message.go` 的 `Chat`、`dispatch`、`sendMsg`、`MsgKey`：一条消息如何找到对方。`models/message_key_test.go` 锁住了键名的顺序。
10. `models/contact.go`、`models/friend_apply.go` 和 `models/Community.go`：好友为什么是两行，申请为什么要先同意。
11. `utils/resp.go`：大写 JSON 的字段。
12. `flow_test.go`：这些接口怎样串成一次完整调用。它就是使用文档第 7 节的自动化版本。

自测需要本机 MySQL 和 Redis：

```powershell
cd D:\golang\GinChat
go test ./...
```

`TestChatFlow` 会自己拉起路由，走完注册、登录、好友、申请、群、私聊、历史消息、上传和错误令牌。
