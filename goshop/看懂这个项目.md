# 看懂 GoShop

把这个项目看成五个 RPC 进程、四个 HTTP 网关、一条加购调用链。按下面这些点看，代码就能对上，不必先把微服务的书读完。

启动、接口和排错仍以 [使用文档.md](使用文档.md) 为准。本文只回答：要懂哪些东西，才算看懂这个项目。

## 先记住项目边界

浏览器不直接打 RPC 端口。它只访问旁边的 Gin 网关，网关再按服务名调用另一个进程里的函数。

```text
浏览器
  → client（Gin，HTTP 网关）
    → handler（RPC 入口，收请求、填响应）
      → domain/service（大多只是把调用交给 repository）
        → domain/repository（写 SQL、读写 Redis）
          → domain/model（表结构）
            → MySQL / Redis
```

端口：

| 做什么 | 浏览器打这里 | 服务之间打这里 |
| --- | --- | --- |
| 登录 | 用户 HTTP `:8088` | 用户 RPC `:8081`，名字 `shop-user` |
| 商品、库存 | 商品 HTTP `:8087` | 商品 RPC `:8082`，名字 `shop-product` |
| 购物车 | 购物车 HTTP `:6668` | 购物车 RPC `:8084`，名字 `shop-cart` |
| 订单 | 订单 HTTP `:6669` | 订单 RPC `:8085`，名字 `trade-order` |
| 支付 | 支付 HTTP `:8086` | 支付回调再 RPC 订单服务 |

`8081`、`8082`、`8084`、`8085` 没有页面。购物车和订单的 HTTP 会被 Chrome 拦截，用 curl 看。

每个服务有自己的 `go.mod`。`goshop/go.work` 把它们和 `common` 放在同一次编译里。公共库的 import 路径是 `git.mashibing.com/msb_47094/shopping-comm`，实际代码在 `goshop/common`。`go run`、`go test`、`go mod tidy` 在对应服务目录里做；在 `goshop` 目录下时，工作区会让这些模块互相看见本地的 `common`。

`*.pb.go`、`*.pb.micro.go` 是生成的，阅读时跳过。改接口要改 `.proto`。

配置 JSON 用 `//go:embed` 打进程序。改完 `config` 必须重新 `go run`。

## 看懂代码所需要的东西

按这个顺序就够。每一项都只要懂到「能解释这个项目里的那一处」。

### 1. 一次加购怎么穿过三个服务

`shoppingCart-service/client/client.go` 的 `/increase` 是整份项目的主线。先看这个函数，不要从头到尾硬读整个文件。

```text
浏览器 GET :6668/increase     请求头 Uuid: 登录返回的 user.id
  → RPC shop-user.GetUserToken      Redis 里有没有这个用户
  → RPC shop-product.ShowProductDetail
  → RPC shop-product.ShowDetailSku  库存够不够
  → RPC shop-product.UpdateSku      先减库存
  → RPC shop-cart.AddCart           往 shopping_cart 插一行
```

调用是同步的：网关发一次 RPC，等对方返回，再发下一次。服务之间不写死 IP。本机没有 Consul 时，go-micro 用 mDNS 互相发现，日志里是 `Registry [mdns]`。本机传输是 HTTP，日志是 `Transport [http]`，不用再开一个 gRPC 端口。

登录的三个条件必须同时满足：`clientId=0`、`systemId=0`、`verificationCode=6666`。手机号第一次出现就插入一行。令牌在 Redis 里放 1 小时，键是用户 ID。`Uuid` 必须等于登录结果里的 `user.id`。

### 2. 库存为什么用增减量，不用覆盖

加购和回滚都改 `product_sku.stock`。如果两个请求各自读出库存再写回一个新数字，后写的会盖掉先写的。

这里的约定在 `common.StockDeltaName`（字符串 `__stock_delta__`）。请求的 `Name` 等于它时，`Stock` 是增减量，不是要写成的绝对库存。SQL 是：

```sql
UPDATE product_sku SET stock = stock + ? WHERE id = ? AND stock + ? >= 0
```

减库存传负数，补偿时把符号反过来。库存不够时这句更新影响 0 行，不会减成负数。

### 3. 下单的 Saga 为什么不能用进程里的全局变量

下单要同时做两件事：把购物车标成已删除，再插入订单。两件事在不同进程、不同库里。DTM 的 Saga 是：先执行正向接口，失败了再按相反顺序调用补偿接口。

- 购物车网关 `:6668`：`/updateSku` 和 `/updateSku-compensate`，`/addCart` 和 `/addCart-compensate`
- 订单网关 `:6669`：`/updateCart` 和 `/updateCart-compensate`，`/addTrade` 和 `/addTrade-compensate`

补偿可能落到另一个请求、甚至另一个进程，所以购物车 ID 和数量不能放在进程全局变量里，要放进这次 Saga 的请求里。购物车 ID 在正向插入之前就定好。补偿把库存增减量的符号反过来。

把订单标成未删除时，GORM 的 `Updates` 会跳过 `false`。回滚必须显式 `Select` 这一列，否则 `is_deleted` 改不回去。

没装 DTM（`http://127.0.0.1:36789`）时，只有 `/addShoppingCart` 和 `/cartAdvanceOrder` 会失败。登录、商品、普通加购不受影响。

### 4. 四张后来补上的表，各自讲一件事

库是启动时自己建的：`user_center`、`product_center`、`trade_center`。购物车表 `shopping_cart` 放在商品库，因为算总价要和 `product_sku` JOIN。列注释在模型的 `gorm` 标签上。

| 表 | 库 | 看它是为了懂什么 |
| --- | --- | --- |
| `user_address` | 用户库 | 一个用户多条地址。校验在 `address.go`，不访问数据库 |
| `product_category` | 商品库 | 商品和分类分开。示例商品的分类是 31 |
| `trade_order_item` | 订单库 | 订单头和订单行拆开。交易服务不能 JOIN 商品库，行上只记购物车 ID 和当时的金额 |
| `trade_order_log` | 订单库 | 状态每次变化留一行 |

订单状态：1 待支付，2 已关闭，3 已支付，4 已发货，5 已收货，6 已完成，7 已追评。更新前先看 `CanTransit`。待支付可以支付或关闭，已发货不能退回待支付。支付回调把状态从 1 改成 3。

### 5. 登录令牌、Redis 和那个二进制键

登录成功后，用户 ID 是键，MD5 令牌是值，过期 1 小时。键不在了就视为未登录。购物车和订单网关每次都会先调用 `GetUserToken`。

课程原来只存二进制形式的键（用户 2 对应 `"10"`）。现在十进制用户 ID 和二进制形式都会写一份，所以请求头填 `2` 或 `10` 都可以。转换函数在 `common/utils.go`，它是教学用的管道示例，不要把它当成 `strconv.Atoi`。

`common/md5.go` 用当前时间做登录令牌。这里只是把一段字符串变成固定长度的十六进制，不是用来保护密码。

### 6. 结构体怎么变成表，JSON 怎么对拷

GORM 把结构体当成表。`ID` 默认是主键，驼峰字段变成下划线列名。`TableName()` 用来指定真实表名，避免被收成复数。`AutoMigrate` 会建表、补列，不会删列。

商品详情、规格列表和购物车算价用了手写 SQL，因为要 JOIN 或 `GROUP_CONCAT`。

`common/resp.go` 的 `SwapToStruct` 先把一个结构体编成 JSON，再解到另一个结构体。数据库结构和 proto 结构对得上，靠的是 `json` 标签。时间类型对字符串时，对不上的字段会是零值，所以有的详情里时间是 `0001-01-01`。

### 7. 支付只负责把状态改成已支付

支付服务不存自己的表。收银台由支付宝或 PayPal 生成。付完款后对方回调本机：支付宝 `POST /return`，PayPal `GET /payPalBack`。回调里再 RPC 订单服务，把 `order_status` 改成 3。

`main.go` 里的密钥是课程沙箱示例。支付宝示例公钥加载失败时，日志写 `alipay ... skipped`，进程仍然听 8086。这段回调只检查通知正文里有没有支付成功，没有做正式的签名校验。

## 建议顺着这 11 个文件读

手写的 `.go` 和 `.proto` 用中文注释说明这个类型或函数在业务里做什么。

1. `user-service/proto/user.proto`：登录的合同，`message` 和 `service`。
2. `user-service/main.go`：怎么读配置、连数据库、把 handler 注册上去。
3. `user-service/handler/user.go`：一次 RPC 怎么填响应。
4. `user-service/domain/repository/user_repository.go`：三条硬编码的登录条件，令牌怎么进 Redis。
5. `user-service/client/user_client.go`：Gin 怎么把查询参数变成 RPC 请求。
6. `product-service/domain/model/product.go` 和 `product_sku.go`：结构体和表的对应关系。
7. `product-service/domain/repository/product_repository.go`：分页，以及库存增减量那条 SQL。
8. `shoppingCart-service/client/client.go` 的 `/increase`：一次业务如何连续调用三个服务。
9. `trade-order/domain/repository/trade_repository.go`：订单头、订单行、状态流水。
10. `trade-order/domain/model/status.go`：哪些状态变化允许。
11. `payment-service/main.go`：支付回调如何找回订单并改状态。

工具函数集中在 `common/config.go`、`utils.go`、`resp.go`、`migrate.go`。

自测不连数据库：

```powershell
cd D:\golang\goshop
go test ./user-service/domain/model/ ./trade-order/domain/model/
```

连上 MySQL 后再启动用户、商品、订单服务，新表才会出现。

## 可以先放着的

Consul 当配置中心、Jaeger 的图、Prometheus 图表、Hystrix 监控页 `:9096` / `:9097`、限流的具体算法、round-robin。本机每个服务只起一份，轮询看不出差别。限流大约每秒放行 `common.QPS`（100）个 RPC，超出就拒绝，知道它套在购物车和订单的 RPC 外面即可。

`compat/microcmd` 只是补 go-micro 删掉的一个空注册表，业务不用读。
